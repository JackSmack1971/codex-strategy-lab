# Controlled capability lifecycle

Discover existing functions and CLI before creating new ones. Inventory references are navigation, not authorization. Inspect scripts/research.py, research/data, experiments, validation and reporting. Candidate -> tested -> reviewed -> operator-approved registration -> fresh-session reuse. Record identifier/version, source digest, input/output contract, data assumptions, side effects, tests and negative cases, reviewer evidence, promotion decision and limitations. A candidate cannot judge its own eligibility or change adjudication. No dynamic import of arbitrary user-supplied paths from an inventory. No new external provider without license/access and explicit scope. Keep registry entries versioned in Git after approval; ledger remains authoritative for research state. Until a promotion mechanism is implemented, use this as a manual review protocol, not an enforcement guarantee.

## Read-only discovery interface

Run `scripts/lab research capability-list` for versioned JSON navigation metadata. It lists the current CLI commands and selected Python-only entry points, distinguishing read-only, derived-only and active-state-writing operations. State-writing entries are supervisor-only under the Phase 6 behavioral contract; this is not a runtime access-control mechanism. The catalog neither constructs a ledger nor accesses datasets, executes a listed capability, or verifies runtime availability or authorization. Inspect the named implementation and tests before use. Python entries are curated, not exhaustive; absence is not proof that a capability does not exist. This is not the approved capability promotion registry. No promotion mechanism or research gate is changed.
